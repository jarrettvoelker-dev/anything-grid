# Anything Grid

轴交叉填词。每格填一个**同时满足它所在各轴条件**的事物。

- **平面题（2D）**：行 × 列，2×2 ～ 5×5
- **立体题（3D）**：三条轴 × 每轴三个特质 = 27 格

**线上：** https://jarrettvoelker-dev.github.io/anything-grid/

## 现在能玩什么

- **2D 空间画布**：无限平面，滚轮/捏合缩放，空格+拖拽平移，Shift 拖拽框选，Delete 清空，Ctrl/Cmd+Z 撤销
- **3D 立方体**：27 个方块摆成 3×3×3，拖动旋转、滚轮/双指缩放、可调方块间距把它拆开看内部
- **3D 平面层**：立方体沿 Z 轴切成三张 3×3，一次看一层 —— 转不明白立方体时用这个。两种视图共用同一份作答
- **两种判定方式**（出题时选）：
  - **预设答案**：出题人给每格写好答案，玩家猜。走精确 → 别名 → 同义词 → 语义 → 类别校验，纯本地
  - **开放造词**：没有标准答案，玩家自己发挥，AI 判「是否符合三项特质」并给冷门度。2D / 3D 都能用
- **创建器**：选维度与判定方式、自定义各轴条件、每格多个正确答案（含别名、同义词、描述、配图）、实时预览、自动存草稿
- **自动填充**：预设答案模式下，已在别处答对的内容遇到同样接受它的空格会自动补上（每次过条件校验）

## 开发

```bash
npm install
npm run dev          # http://localhost:5173
npm test             # 单元测试：匹配引擎 + 撤销栈
bash scripts/run_e2e.sh   # 端到端：真浏览器里驱动 UI（需要 Windows 自带 Edge）
npm run build        # 构建到 dist/
bash scripts/deploy.sh    # 发布到 GitHub Pages
node scripts/verify_live.mjs   # 线上验收：驱动**已部署的站点**（需要 Windows 自带 Edge）
```

> 部署走「本地构建 + 推 `gh-pages` 产物」，不用 GitHub Actions —— 本机 gh token 没有
> `workflow` 作用域，推不了 workflow 文件。`dist/` 在源码仓库里是 gitignore 的。
> 若 `github.com` 的 HTTPS 不通（表现为 `GnuTLS recv error`），deploy.sh 会自动
> 退到 `scripts/push_pages.py`，走 GitHub 的 Git Data API 推同样的内容。

三层测试各管一段，别互相替代：`npm test` 证明引擎对，`run_e2e.sh` 证明本地构建里
UI 真的接上了，`verify_live.mjs` 证明**用户打开那个网址时能用**。

## 架构

```
src/
├── lib/
│   ├── match.ts      相似搜索流水线（纯函数，语义档可注入 resolver）
│   ├── judge.ts      开放造词的 AI 裁判（玩家 BYOK，纯解析函数可单测）
│   ├── history.ts    快照式撤销栈（带合并，拖拽不会塞满记录）
│   ├── types.ts      数据模型 v2（N 轴统一模型 + v1 迁移）
│   ├── storage.ts    本地存档（M2 换成服务端后降级为草稿箱）
│   └── samples.ts    示例题库（2D 四套 + 3D 两套）
├── state/store.ts    单 store：文档 + 历史 + 选择 + 视口 + 裁判配置
├── components/
│   ├── CanvasPlane.tsx  无限画布（手势矩阵、惯性、缩放锚点）
│   ├── Board.tsx        2D 棋盘（渲染在画布的世界坐标层里）
│   ├── Cube3D.tsx       3D 立方体（旋转/缩放直接写 DOM transform，不进 React）
│   ├── Flat3D.tsx       3D 平面层 + 轴图例
│   ├── JudgeSettings.tsx AI 裁判配置
│   └── ui.tsx           设计系统基元
└── views/               Home / Play / Creator
```

## 路线图

- [x] **M1** 前端底座 + 2D 画布 + 核心玩法 + 创建器
- [x] **M1.5** 3D 深度合并进同一套题（统一 N 轴模型、两种判定模式、立方体/平面层双视图）
- [ ] **M2** 后端（Cloudflare Workers + D1）：答案移到服务端、发布状态、`/grid/:id` 稳定链接
- [ ] **M3** 服务端相似搜索 + 创建者 BYOK 语义档 + 结果分享卡片
- [ ] **M4** 限流与答案隐藏审计

## 关键设计决定

**为什么答案判定要走服务端（M2）**：现在答案存在浏览器里，打开开发者工具就能看光。
M2 会把判定挪到服务端，前端只拿得到"对/错/接近 + 置信度"。

**为什么语义档的 API Key 必须由创建者提供**：语义匹配要把答案和猜测一起喂给模型。
如果 Key 是玩家的，玩家可以把接口地址指到自己的服务器，从而读到答案。
创建者本来就知道答案，所以只有创建者提供 Key 才不产生新的泄露面。

**为什么开放造词的 Key 反而是玩家的**：这一档题目里**根本不存在标准答案**，
判定要问的只有「这三项特质 + 玩家自己刚敲的那个词」。玩家就算把接口指到自己的服务器，
能拿到的也只是他自己已经知道的东西 —— 没有可泄露的对象。所以走玩家 BYOK 既安全、
又不用宿主掏钱。这两条路径独立，别把它们合并。

**为什么"判定失败"必须是一个独立状态**：网关挂了、没配 Key、模型返回了非 JSON —— 这些
都不是"你答错了"。把它显示成红叉是在骗玩家，会让人以为自己的答案有问题而反复改。
`CellStatus` 里 `error` 单列，配色是中性的虚线环而不是红色，且不计入完成进度。
